**適用範囲：** AWS シンガポールリージョンにデプロイされた Tier0 Cloud の本番 SaaS サービス。\
**文書日付：** 2026 年 10 月 22 日

Tier0 Cloud は、ネットワークアクセス制御、テナント分離、ID とアクセスの管理、データ暗号化、バックアップと復旧によって、ネットワーク攻撃や不正アクセスのリスクを低減します。本書では、プラットフォームのセキュリティ対策と、セキュリティインシデントが他のテナント、プラットフォーム内部のサービス、お客様のネットワークへ波及することを抑える制御の境界について説明します。

:::note[Edge エディション]
この説明は Tier0 Cloud のみに適用されます。Edge のセットアップについては、[インストール](../../get-started/installation/)を参照してください。
:::

## 1 ネットワーク境界とアクセス制御

Tier0 Cloud の公開 Web および API へのアクセスは TLS で暗号化され、統一されたエッジ入口とアプリケーションゲートウェイを経由します。主要サービスの入口ではオリジンへのアクセスを検証し、検証要件を満たさない直接アクセスを拒否することで、エッジ入口を迂回したオリジンへのアクセスリスクを低減します。

本番環境は、クラウドアカウント、ネットワーク、クラスター、データベースの各層で開発環境およびステージング環境から分離され、アクセス認証情報も個別に管理されます。本番環境への管理アクセスには、認証済みの専用ネットワーク経路を使用します。

## 2 テナント分離とインシデントの波及防止

### 2.1 ワークロードの分離

テナントのワークロードは個別の Kubernetes 名前空間で実行され、専用ノードプールとスケジューリング制約によって、プラットフォームのサービスおよび管理コンポーネントから分離されます。この仕組みは、テナントのアプリケーションとプラットフォームのコンポーネントが直接接触する範囲を制限し、あるアプリケーションでセキュリティインシデントが発生した場合の他のサービスへの影響を低減します。

### 2.2 ネットワークの分離

テナントの名前空間に対する受信・送信通信には、デフォルトで拒否し、明示的なルールでのみ許可するネットワークポリシーを適用します。プラットフォームがポリシーを自動的に設定・同期し、クラスターのネットワークコンポーネントが適用します。

受信通信は、同一テナントのワークロードと、必要な業務機能を担うプラットフォームサービスからの通信に限定されます。送信通信は、クラスター内の DNS 名前解決、同一テナントのサービス、指定されたプラットフォームゲートウェイ、メッセージングサービス、割り当てられたデータベースエンドポイントに対して、ルールに従って許可されます。パブリックインターネットへのアクセスもネットワークポリシーの制約を受けます。明示的に許可された業務上の依存先を除き、プライベートネットワークアドレスへのアクセスを制限し、クラウドインスタンスのメタデータアドレスへの直接アクセスを遮断します。

これらの対策は、許可されていないテナント間接続や、テナントのワークロードからプラットフォーム内部ネットワークへのラテラルムーブメントを制限します。あるテナントのアプリケーションでセキュリティインシデントが発生しても、それだけで他のテナントやプラットフォームの管理コンポーネントへのアクセス権限が付与されることはありません。許可済みの業務接続にも、対応するネットワークルールと ID・アクセス制御が適用されます。

### 2.3 データと ID の分離

テナントのアプリケーションデータは、データベース層で論理的に分離されます。個別のデータベース単位が割り当てられる場合は、ネットワークアクセスルールによって接続元も制限されます。

プラットフォームはサービスの役割に応じてアクセス権限を設定し、各ワークロードがアクセスできるリソースを必要な機能の範囲に限定します。ネットワーク分離と ID に基づく認可を組み合わせることで、影響を受けたワークロードがアクセスできるリソースの範囲を制限します。

### 2.4 お客様のネットワークへの接続境界

本節のテナント分離対策は、Tier0 Cloud のプラットフォーム内部に適用されます。お客様がコネクター、ゲートウェイ、その他の連携方式で内部システムを接続する場合、お客様のネットワークへのアクセス境界は、実際の接続方式、ルーティング、ファイアウォールルール、使用する認証情報に付与された権限にも依存します。

接続時には、業務に必要な宛先アドレス、ポート、アカウント権限だけを許可し、接続コンポーネントと他の内部システムをネットワーク上で分離してください。プラットフォーム内部の分離は、お客様側のネットワークアクセス制御を代替するものではありません。双方が具体的な接続構成に基づいてアクセス範囲を決定・検証し、許可済みの接続を経由して他の内部システムへ影響が波及するリスクを抑える必要があります。

## 3 データ保護

プラットフォームは、データの転送、保存、アクセスに対して次の保護対策を実施します。

- 公開 Web および API の通信と、マネージドデータベースおよびキャッシュへのアクセスに TLS 暗号化を使用します。
- マネージドデータベース、キャッシュ、オブジェクトストレージでは保存時の暗号化を有効にします。
- オブジェクトストレージではパブリックアクセスをブロックし、暗号化要件、HTTPS 接続要件、リソース権限によってデータアクセスを制限します。
- テナントデータへのアクセスには、データベース分離と ID・アクセス制御の両方を適用します。

## 4 バックアップと復旧

Tier0 Cloud は、本番データベースと、バックアップ対象に含まれるサービス単位のデータベースをバックアップします。バックアップデータはアクセスが制限された専用のオブジェクトストレージに保存され、対応する保持ポリシーに従って管理されます。

バックアップジョブには専用の ID を使用し、指定された保存先で必要な読み取り・書き込み操作だけを許可します。バックアップオブジェクトの削除権限は付与しません。保持期限が切れたバックアップはストレージのライフサイクルルールで削除し、バックアップ用の認証情報が漏えいした場合に復旧用データが削除されるリスクを低減します。

バックアップ完了後は整合性を確認し、分離された環境でのリストア検証によってバックアップが利用可能であることを確認します。アプリケーション設定はバージョン管理し、ビルド成果物は非公開のコンテナーイメージレジストリに保存することで、サービスの復旧とバージョンのロールバックを支援します。

## 5 管理アクセスと本番環境の変更

本番環境への管理アクセスには、個人ごとに割り当てられた ID を使用し、最小権限の原則に従って権限を付与します。機密性の高い操作を行うコンソールの ID には、多要素認証を必須とします。

日常点検には、ワークロードの状態、ログ、イベントを参照できる制限付きの読み取り専用 ID を使用します。この ID では、機密性の高い認証情報の読み取り、リソースの変更、リモートコマンドの実行はできません。本番環境の変更には、個別に認可された ID と手順を使用します。

インフラストラクチャ設定、デプロイマニフェスト、運用スクリプトはバージョン管理します。本番環境の変更では、目的、影響範囲、検証手順、ロールバック計画を明確にし、実行者の ID、設定差分、検証結果を記録して、追跡と復旧を可能にします。

## 6 監視とセキュリティインシデント対応

プラットフォームは、本番環境の稼働メトリクス、ログ、健全性情報を集約し、異常アラートを運用対応チャネルへ送信します。監視対象には、サービスの可用性、エラー率、データベースの健全性、証明書の有効期限、バックアップジョブの状態、クラスターの稼働状態が含まれます。

セキュリティインシデントが発生した場合は、影響範囲の封じ込めを優先し、関連するログ、設定、発生から対応までの時系列記録を保全します。必要な隔離と調査を完了した後にサービスを復旧し、その後、振り返りと是正措置の進捗管理を行います。インシデント対応中の本番環境の変更も、所定の手順に従って認可・記録します。

## 7 セキュリティに関するお問い合わせ

セキュリティ評価、お客様によるデューデリジェンス、脆弱性の疑いについては、Tier0 の担当者またはセキュリティチームにお問い合わせください。非公開のアーキテクチャや制御の詳細は、適切な秘密保持の取り決めの下で提供できる場合があります。初回のお問い合わせには、アクセス認証情報、秘密鍵、お客様の機密データを含めないでください。
