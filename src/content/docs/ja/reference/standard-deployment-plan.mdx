## 目的

簡易構成では Docker Swarm を使用せず、単一の `enterprise` アプリケーションノードを配置します。仮想マシンは合計 `4` 台です。

- `1` 台の enterprise ノードで `tier0-enterprise + EMQX` を実行します。
- `2` 台のデータベースノードで PostgreSQL + TimescaleDB のプライマリ／スタンバイクラスターを構成します。
- `1` 台の Witness ノードがデータベースの監視、クォーラム判定、フェイルオーバーに参加します。

簡易構成はデプロイの複雑さを低減します。一方、アプリケーション層と EMQX は単一障害点となります。`DB VIP + Witness` による高可用性を維持するのはデータベース層のみです。

## IP アドレス計画

以下の IP アドレスは計画用のプレースホルダーです。実装前に現場の実際のネットワークに合わせて置き換えてください。

| 種別 | 名前 | 計画 IP | 説明 |
| --- | --- | --- | --- |
| アプリケーションノード | `ent-enterprise-01` | `10.60.10.11` | `tier0-enterprise + EMQX` を実行する単一の enterprise ノード |
| 論理エンドポイント | `DB VIP` | `10.60.20.10` | 現在のプライマリのみを指す共通データベースエンドポイント |
| データベースノード | `ent-db-01` | `10.60.20.11` | PostgreSQL + TimescaleDB のプライマリ候補 |
| データベースノード | `ent-db-02` | `10.60.20.12` | PostgreSQL + TimescaleDB のスタンバイ候補 |
| クォーラムノード | `ent-db-witness-01` | `10.60.20.13` | `repmgr witness`／データベースのクォーラム監視 |

## 全体トポロジー

<img width={650} src="https://enterpriseimage.oss-cn-hangzhou.aliyuncs.com/9.png" />

主要な経路：

- 業務経路：クライアント／現場システム → `ent-enterprise-01` → `DB VIP` → 現在のプライマリデータベース。
- `tier0-enterprise` と `EMQX` は、どちらも `ent-enterprise-01` 上で実行します。
- データベースへのアクセスには必ず `DB VIP` を使用し、アプリケーションから `ent-db-01/02` への直接アクセスは禁止します。
- `Witness` はデータベースのクォーラム判定、昇格、健全性確認のみに参加し、業務経路には含まれません。

## データベースの監視とフェイルオーバー

| フェーズ | 経路 | 説明 |
| --- | --- | --- |
| 通常のアクセス | `ent-enterprise-01 -> DB VIP -> current primary` | アプリケーションは常に `10.60.20.10:5432` に接続します |
| 通常のレプリケーション | `current primary -> current standby` | PostgreSQL WAL ストリーミングレプリケーション |
| 通常の監視 | `DB-01/DB-02 -> Witness` | `repmgrd` が状態を報告し、Witness がクォーラム判定に参加します |
| プライマリ障害 | `standby -> Witness` | スタンバイがクォーラム確認を要求し、スプリットブレインを防止します |
| スタンバイの昇格 | `standby promote` | Witness の確認後にスタンバイを昇格させます |
| VIP の移動 | `DB VIP -> new primary` | `10.60.20.10` を新しいプライマリに割り当てます |
| アプリケーションの復旧 | `ent-enterprise-01 -> DB VIP -> new primary` | 接続プールの再接続後にアプリケーションが復旧します |

| 分類 | 台数 | ノードごとの仕様 | vCPU 小計 | メモリー小計 | ストレージ小計 |

| PostgreSQL + TimescaleDB ノード | `2` | `4C / 8G / 500G` | `8C` | `16G` | `1000G` |

合計値：

- 仮想マシン：`4` 台
- vCPU：`18`
- メモリー：`52G`
- ストレージ：`1.14T`

## デプロイの推奨事項

### enterprise アプリケーションノード

- Docker Swarm はデプロイしません。
- `tier0-enterprise` と `EMQX` を同一の `ent-enterprise-01` ノードにデプロイします。
- `ent-enterprise-01` はアプリケーション層の単一障害点です。障害時は手動で復旧するか、バックアップから再構築します。
- このノードには `100G` のシステムディスクが 1 台しかないため、業務データの長期保存には適しません。
- `tier0-enterprise` の業務データは PostgreSQL/TimescaleDB に保存する必要があります。
- アップロード、インポート／エクスポート、レポートのファイルはローカルに保存してバックアップできます。後で標準構成へ移行する場合は、これらのファイルを NFS/NAS またはオブジェクトストレージへ移行してください。

### 単一ノードの EMQX

- 簡易構成の EMQX は、単一ノードのステートフルサービスです。
- データディレクトリを `ent-enterprise-01` 上に固定します。例：`/data/emqx`。
- 設定、証明書、プラグイン、ルールエンジンの設定をバックアップします。
- メッセージ層の高可用性は提供しません。これが要件を満たさない場合は、3 ノードの EMQX クラスターを持つ標準構成を使用してください。

### PostgreSQL + TimescaleDB

- PostgreSQL：`16` または現場で検証済みのバージョン。
- TimescaleDB：選択した PostgreSQL のメジャーバージョンと互換性のある安定版。
- レプリケーション：物理ストリーミングレプリケーション。
- フェイルオーバー：`repmgrd + witness`。
- データベースの入口：`DB VIP`。
- 接続プール：`ent-enterprise-01` 上で PgBouncer を実行し、データベースへの接続負荷を低減できます。

### Witness

- Witness は `repmgr witness` のメタデータと監視ロジックのみを保持します。
- Witness は業務 SQL を処理しません。
- Witness の障害で現在のプライマリは停止しませんが、自動フェイルオーバーの信頼性は低下します。

## 高可用性の機能と障害の境界

| 障害シナリオ | 想定される動作 | 業務への影響 |
| --- | --- | --- |
| `ent-enterprise-01` の障害 | アプリケーションと EMQX が停止し、手動復旧またはバックアップからの再構築が必要です | アプリケーション層が全面停止します |
| 現在の DB プライマリの障害 | Witness のクォーラム確認後にスタンバイが昇格し、DB VIP が移動します | 数秒から数分の書き込み中断。アプリケーションの再接続が必要です |
| DB スタンバイの障害 | プライマリは稼働を継続し、レプリケーションのアラートが発生します | 直接の業務停止はありませんが、DB のホットスタンバイを失います |
| Witness の障害 | 現在のプライマリは稼働を継続しますが、自動フェイルオーバーの信頼性が低下します | 直接の業務停止はありません。Witness を優先して復旧します |
| DB VIP の移動失敗 | 新しいプライマリが存在しても、共通の入口に到達できない場合があります | 業務が停止します。VIP の手動割り当てが必要です |

## 本番稼働前のチェックリスト

| 確認項目 | 合格基準 |
| --- | --- |
| 4 台の仮想マシンのホスト名が固定されている | `hostnamectl` が計画と一致します |
| 共通の SSH 接続が利用できる | 運用端末から鍵認証で 4 台すべてにアクセスできます |
| 時刻同期 | 4 台間の時刻差が `1s` 未満です |
| ファイアウォールが許可されている | 第 9 節のポートが定められた範囲で許可されています |
| enterprise サービスが正常である | `tier0-enterprise` のヘルスチェックに合格します |
| EMQX の状態が検証されている | EMQX ノード、待ち受けポート、永続化ディレクトリが正常です |
| enterprise のディスク使用率が安全な範囲にある | `/` の使用率が `70%` 未満で、ログとキャッシュのクリーンアップが設定されています |
| DB のプライマリ／スタンバイが正常である | `repmgr cluster show` でプライマリ、スタンバイ、Witness が正常です |
| DB VIP が利用できる | enterprise ノードから `10.60.20.10:5432` に接続できます |
| DB プライマリのフェイルオーバー訓練 | スタンバイの昇格と DB VIP の移動ができます |
| バックアップのリストア訓練 | テスト用データベースへバックアップをリストアできます |

## 実装の順序

1. 4 台の仮想マシンを作成し、ホスト名、IP、時刻同期、SSH を設定します。
2. OS の基本設定、ファイアウォール、マウント、カーネルパラメーターを初期化します。
3. `ent-enterprise-01` に `tier0-enterprise` をデプロイします。
4. `ent-enterprise-01` に単一ノードの EMQX をデプロイします。
5. PostgreSQL + TimescaleDB のプライマリ／スタンバイをデプロイします。
6. repmgr witness、repmgrd、DB VIP 移動スクリプトをデプロイします。
7. 接続、EMQX の復旧、データベースのフェイルオーバー、バックアップのリストア、日常点検を検証します。
8. 運用 Runbook、認証情報の保管、日常点検タスクを整備します。

## リスクと未確定事項

- 簡易構成にはアプリケーション層の単一障害点があります。`ent-enterprise-01` が停止すると、業務サービス全体が利用できなくなります。
- EMQX は単一ノードであり、メッセージ層の高可用性を提供しません。
- `ent-enterprise-01` のシステムディスクは `100G` の 1 台のみです。ログ、キャッシュ、添付ファイル、一時ファイルの使用量を管理する必要があります。
- 後でアプリケーション層または EMQX の高可用性が必要になった場合は、標準構成へ移行します。
- データベースの RPO/RTO は未確定です。このプライマリ／スタンバイ構成はデータ損失ゼロを保証しません。
- DB VIP 移動スクリプトは現場での検証が必要です。特に、仮想化／ネットワーク基盤が VRRP を許可していることを確認してください。
