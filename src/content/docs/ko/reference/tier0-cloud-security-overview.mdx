**적용 범위:** AWS 싱가포르 리전에 배포된 Tier0 Cloud 프로덕션 SaaS 서비스.\
**문서 날짜:** 2026년 10월 22일

Tier0 Cloud는 네트워크 접근 제어, 테넌트 격리, ID 및 접근 관리, 데이터 암호화, 백업 및 복구를 통해 네트워크 공격과 무단 접근의 위험을 줄입니다. 이 문서는 플랫폼의 보안 조치와 보안 사고가 다른 테넌트, 플랫폼 내부 서비스 및 고객 네트워크로 확산되는 것을 제한하는 통제 경계를 설명합니다.

:::note[Edge 에디션]
이 안내는 Tier0 Cloud에만 적용됩니다. Edge 설정은 [설치](../../get-started/installation/)를 참조하세요.
:::

## 1 네트워크 경계 및 접근 제어

Tier0 Cloud의 공개 Web 및 API 접근에는 TLS 암호화를 사용하며, 통합된 엣지 진입점과 애플리케이션 게이트웨이를 거칩니다. 핵심 서비스 진입점은 원본 서버 접근을 검증하고, 검증 요건을 충족하지 않는 직접 접근 요청을 거부하여 엣지 진입점을 우회한 원본 서버 접근 위험을 줄입니다.

프로덕션 환경은 클라우드 계정, 네트워크, 클러스터 및 데이터베이스 계층에서 개발·스테이징 환경과 격리되며, 접근 자격 증명도 별도로 관리합니다. 프로덕션 관리 접근에는 인증된 전용 네트워크 경로를 사용합니다.

## 2 테넌트 격리 및 사고 확산 방지

### 2.1 워크로드 격리

테넌트 워크로드는 별도의 Kubernetes 네임스페이스에서 실행되며, 전용 노드 풀과 스케줄링 제약을 통해 플랫폼 서비스 및 관리 구성 요소와 분리됩니다. 이 방식은 테넌트 애플리케이션과 플랫폼 구성 요소 사이의 직접적인 상호 작용 범위를 제한하여, 특정 애플리케이션에서 보안 사고가 발생했을 때 다른 서비스에 미치는 영향을 줄입니다.

### 2.2 네트워크 격리

테넌트 네임스페이스의 인바운드 및 아웃바운드 통신에는 기본적으로 거부하고 명시적인 규칙으로만 허용하는 네트워크 정책을 적용합니다. 플랫폼은 정책을 자동으로 구성하고 동기화하며, 클러스터 네트워크 구성 요소가 이를 적용합니다.

인바운드 통신은 동일 테넌트의 워크로드와 필수 업무 기능을 수행하는 플랫폼 서비스에서 오는 통신만 허용합니다. 아웃바운드 통신은 규칙에 따라 클러스터 DNS 이름 확인, 동일 테넌트의 서비스, 지정된 플랫폼 게이트웨이, 메시징 서비스 및 할당된 데이터베이스 엔드포인트에 대해 허용합니다. 공용 인터넷 접근도 네트워크 정책의 제약을 받습니다. 명시적으로 허용된 업무 의존 대상을 제외하고 사설 네트워크 주소 접근을 제한하며, 클라우드 인스턴스 메타데이터 주소에 대한 직접 접근을 차단합니다.

이러한 조치는 승인되지 않은 테넌트 간 연결과 테넌트 워크로드에서 플랫폼 내부 네트워크로의 측면 이동을 제한합니다. 특정 테넌트 애플리케이션에서 보안 사고가 발생하더라도 그 사실만으로 다른 테넌트나 플랫폼 관리 구성 요소에 접근할 수 있는 권한이 부여되지는 않습니다. 이미 승인된 업무 연결에도 해당 네트워크 규칙과 ID 및 접근 제어가 계속 적용됩니다.

### 2.3 데이터 및 ID 격리

테넌트 애플리케이션 데이터는 데이터베이스 계층에서 논리적으로 격리됩니다. 별도의 데이터베이스 단위가 할당되는 경우에는 네트워크 접근 규칙을 통해 연결 출발지도 제한합니다.

플랫폼은 서비스 역할에 따라 접근 권한을 설정하고 각 워크로드의 리소스 접근 범위를 필요한 기능으로 제한합니다. 네트워크 격리와 ID 기반 인가를 함께 적용하여 영향을 받은 워크로드가 접근할 수 있는 리소스 범위를 제한합니다.

### 2.4 고객 네트워크 접근 경계

이 절의 테넌트 격리 조치는 Tier0 Cloud 플랫폼 내부에 적용됩니다. 고객이 커넥터, 게이트웨이 또는 기타 통합 방식으로 내부 시스템을 연결하는 경우, 고객 네트워크의 접근 경계는 실제 연결 방식, 라우팅, 방화벽 규칙 및 사용된 자격 증명에 부여된 권한에도 영향을 받습니다.

고객은 업무에 필요한 대상 주소, 포트 및 계정 권한만 허용하고, 연결 구성 요소를 다른 내부 시스템과 네트워크상에서 분리해야 합니다. 플랫폼 내부 격리는 고객 측 네트워크 접근 제어를 대체할 수 없습니다. 양측은 구체적인 연결 구성에 따라 접근 범위를 정하고 검증하여, 승인된 연결을 통해 고객의 다른 시스템으로 사고가 확산될 위험을 제한해야 합니다.

## 3 데이터 보호

플랫폼은 데이터 전송, 저장 및 접근에 다음 보호 조치를 적용합니다.

- 공개 Web 및 API 통신과 관리형 데이터베이스 및 캐시 접근에 TLS 암호화를 사용합니다.
- 관리형 데이터베이스, 캐시 및 객체 스토리지에는 저장 데이터 암호화를 활성화합니다.
- 객체 스토리지는 공개 접근을 차단하며, 암호화 요건, HTTPS 접근 요건 및 리소스 권한을 통해 데이터 접근을 제한합니다.
- 테넌트 데이터 접근에는 데이터베이스 격리와 ID 및 접근 제어가 모두 적용됩니다.

## 4 백업 및 복구

Tier0 Cloud는 프로덕션 데이터베이스와 백업 범위에 포함된 서비스별 데이터베이스를 백업합니다. 백업 데이터는 접근이 제한된 전용 객체 스토리지에 저장하며, 해당 보존 정책에 따라 관리합니다.

백업 작업은 별도의 ID를 사용하며, 지정된 저장 위치에서 필요한 읽기 및 쓰기 작업만 허용합니다. 백업 객체를 삭제할 권한은 부여하지 않습니다. 보존 기간이 지난 백업은 스토리지 수명 주기 규칙으로 삭제하여, 백업 자격 증명이 유출되었을 때 복구 데이터 삭제에 악용될 위험을 줄입니다.

백업이 완료되면 무결성을 확인하고, 격리된 환경에서 복원 검증을 수행하여 백업의 사용 가능 여부를 확인합니다. 애플리케이션 구성은 버전 관리하며, 빌드 산출물은 비공개 컨테이너 이미지 레지스트리에 저장하여 서비스 복구와 버전 롤백을 지원합니다.

## 5 관리 접근 및 프로덕션 변경

프로덕션 관리 접근에는 개인별로 할당된 ID를 사용하고 최소 권한 원칙에 따라 권한을 부여합니다. 민감한 작업에 사용하는 콘솔 ID에는 다중 요소 인증을 의무화합니다.

일상 점검에는 워크로드 상태, 로그 및 이벤트를 확인할 수 있는 제한된 읽기 전용 ID를 사용합니다. 이 ID로는 민감한 자격 증명 읽기, 리소스 수정 또는 원격 명령 실행을 할 수 없습니다. 프로덕션 변경에는 별도로 승인된 ID와 절차를 사용합니다.

인프라 구성, 배포 매니페스트 및 운영 스크립트는 버전 관리합니다. 프로덕션 변경 시에는 목표, 영향 범위, 검증 단계 및 롤백 계획을 명확히 하고, 실행 ID, 구성 차이 및 검증 결과를 기록하여 추적과 복구를 지원합니다.

## 6 모니터링 및 보안 사고 대응

플랫폼은 프로덕션 환경의 운영 지표, 로그 및 상태 정보를 중앙에서 수집하고, 이상 알림을 운영 대응 채널로 전송합니다. 모니터링 범위에는 서비스 가용성, 오류율, 데이터베이스 상태, 인증서 유효성, 백업 작업 상태 및 클러스터 운영 상태가 포함됩니다.

보안 사고가 발생하면 영향 범위의 확산을 막는 데 우선순위를 두고 관련 로그, 구성 및 사고 타임라인을 보존합니다. 필요한 격리와 조사를 완료한 후 서비스를 복구하고, 이후 사고 검토와 시정 조치 추적을 수행합니다. 사고 대응 중의 프로덕션 변경도 정해진 절차에 따라 승인하고 기록합니다.

## 7 보안 문의

보안 평가, 고객 실사 또는 의심되는 취약점에 관해서는 Tier0 고객 담당자나 보안팀에 문의하세요. 비공개 아키텍처 및 통제 세부 정보는 적절한 비밀 유지 약정에 따라 제공될 수 있습니다. 최초 문의에는 접근 자격 증명, 개인 키 또는 고객의 민감한 데이터를 포함하지 마세요.
