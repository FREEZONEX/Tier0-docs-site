이 문서는 Enterprise New offline application을 기준으로 합니다.

## 일일 점검

<Steps>
1. deployment package root directory에서 아래 command를 실행합니다.
    ```bash
    ./bin/verify.sh --site config/site.conf
    ./bin/smoke-business-emqx.sh --site config/site.conf
    ```
2. 다음 항목을 확인합니다.
    - 3개의 Swarm node가 `Ready` 상태입니다.
    - `APP VIP /healthz`와 `/readyz`가 `200`을 반환합니다.
    - `DB VIP:5432`에 접근할 수 있습니다.
    - PostgreSQL primary, standby, witness topology가 정상입니다.
    - `backend`, `redis`, `emqx`, `sourceflow`, `eventflow`, `marimo`, `opcua-server`가 active application node에서 모두 실행 중입니다.
</Steps>
## Application 점검
<Steps>
1. active application node에서 아래 command를 실행합니다.
    ```bash
    cd /opt/tier0-enterprise/tier0-deploy
    bash bin/compose.sh ps
    bash bin/compose.sh logs --tail=200 backend
    curl -fsS http://127.0.0.1:8088/healthz
    curl -fsS http://127.0.0.1:8088/readyz
    ```
    :::note
    `bin/compose.sh`를 우회해 raw `docker compose` command를 직접 실행하지 마세요. 이 wrapper script는 installer가 생성한 runtime environment를 로드합니다.
    :::
2. Health-check 해석:
    - `healthz` 실패: 먼저 backend process, image, container log를 확인합니다.
    - `readyz` 실패: DB VIP, Redis, database migration log도 확인합니다.
    - home page는 접근되지만 login이 불가능한 경우: `.env`의 `ADMIN_INITIAL_PASSWORD`를 확인한 뒤 backend IAM migration log와 user table을 확인합니다. HTTP port만으로 deployment 성공을 판단하지 마세요.
</Steps>
## Protocol Entry 점검

```bash
nc -vz <APP_VIP> 1883
nc -vz <APP_VIP> 8883
nc -vz <APP_VIP> 8083
nc -vz <APP_VIP> 8084
nc -vz <APP_VIP> 4840
```
:::note
EMQX와 OPC UA Server는 active application node에 고정됩니다. APP VIP failover는 `APP VIP:80` HTTP entry만 보장합니다. protocol port는 HAProxy TCP proxying을 통해 routing되지 않으므로, 이 설계는 protocol entry의 high availability를 약속하지 않습니다.
:::
## Database 점검

database node에서 아래 command를 실행합니다.

```bash
systemctl status tier0-postgresql
systemctl status tier0-repmgrd
sudo -iu postgres psql -Atqc 'select pg_is_in_recovery();'
sudo -iu postgres /usr/local/bin/repmgr -f /etc/repmgr.conf cluster show
```

- `pg_is_in_recovery=false`는 primary를 의미합니다.
- `pg_is_in_recovery=true`는 standby를 의미합니다.
- DB VIP는 반드시 현재 primary에만 위치해야 합니다.
- standby replication이 중단되었거나 witness가 upstream error를 보고하면 먼저 site를 보존하세요. 전체 deployment를 바로 다시 실행하지 마세요.

## APP VIP Failover
<Steps>
1. test 전에 현재 VIP를 소유한 node를 기록하고 아래 항목을 검증합니다.

    ```bash
    curl -fsS http://<APP_VIP>/healthz
    curl -fsS http://<APP_VIP>/readyz
    ```

2. 현재 VIP node에서 `keepalived`를 중지한 뒤 다른 application node로 VIP가 takeover되었는지 확인하고 두 URL을 다시 test합니다. HAProxy backend는 `8088/TCP`의 active application node를 가리키므로 세 application node 모두 active node의 port 8088에 접근할 수 있어야 합니다.

3. `keepalived`를 복구한 뒤 `verify.sh`와 smoke check를 다시 실행합니다. drill 중에는 active application container를 중지하지 마세요.
</Steps>
## DB Primary 장애 전환

장애 drill 전에 backup을 만들고 replication이 healthy인지 확인합니다.

```bash
./bin/backup-db.sh --site config/site.conf
```

현재 primary에서 `tier0-postgresql`을 중지한 뒤 `repmgr`이 standby를 promote하고 DB VIP가 takeover되는지 관찰합니다. 목표 RTO는 2분 이내입니다. 같은 architecture의 과거 test에서는 약 59-64초였습니다.
:::caution
- 기존 primary를 production topology에 바로 다시 시작하면 안 됩니다. 먼저 PostgreSQL, repmgrd, keepalived를 중지하고 남아 있는 DB VIP를 제거한 뒤, 현재 새 primary에서 basebackup을 실행하고 node를 standby로 등록한 다음 witness를 다시 연결합니다.
- failover 후 전체 installer를 바로 다시 실행하지 마세요. inventory의 static primary/standby definition이 현재 topology를 방해할 수 있습니다.
:::
## Backup 및 Restore

- Backup:

    ```bash
    ./bin/backup-db.sh --site config/site.conf
    ```

- Restore:

    ```bash
    ./bin/restore-db.sh --site config/site.conf --restore-file /backup/tier0-db/postgres-YYYYmmddTHHMMSS.dump
    ```
:::note
restore 전에 현재 primary를 확인하세요. restore 후 `verify.sh`, smoke check, default-user path의 실제 platform login verification을 실행합니다.
:::
## Cleanup 및 Retest

```bash
./full-cleanup.sh --env install.env --yes
./install.sh --auto --yes
```
:::caution
Full cleanup은 6개 node의 Tier0 runtime data, Docker/Swarm data, database backup을 삭제합니다. 또한 control container가 종료된 뒤 control node에서 final cleanup을 수행합니다. 이 entry는 disposable test environment임이 확인된 경우에만 사용하세요. customer data 또는 incident site를 보존해야 하는 경우 normal `--cleanup`을 사용하고 먼저 backup을 완료하세요.
:::
## 일반적인 문제

### Backend 시작 실패

```bash
cd /opt/tier0-enterprise/tier0-deploy
bash bin/compose.sh logs --tail=300 backend
bash bin/compose.sh ps
```
:::note
DB URL, DB VIP, Redis, migration, mounted directory permission에 집중하세요.
:::
### EMQX 시작 실패

```bash
cd /opt/tier0-enterprise/tier0-deploy
bash bin/compose.sh logs --tail=200 emqx
```
:::note
certificate, configuration file, volume permission, port `1883/8883/8083/8084` 점유 여부를 확인하세요.
:::
### repmgrd 반복 재시작

```bash
systemctl status tier0-repmgrd
tail -100 /var/log/repmgr/repmgr.log
sudo -iu postgres psql -Atqc 'show shared_preload_libraries;'
```
:::note
`shared_preload_libraries`에 `repmgr`가 포함되어 있고 systemd unit이 `repmgrd --daemonize=false`를 사용하는지 확인하세요.
:::
### Material 검증 실패

```bash
./bin/verify-materials.sh
```
:::caution
SHA256 verification을 건너뛰고 deployment를 계속하지 마세요. delivery package를 다시 받거나 traceable process에 따라 material을 rebuild하세요.
:::
