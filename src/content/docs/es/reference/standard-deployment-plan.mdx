## Objetivo

La configuración simplificada no utiliza Docker Swarm. Despliega un único nodo de aplicación `enterprise`, con un total de `4` máquinas virtuales:

- `1` nodo enterprise aloja `tier0-enterprise + EMQX`.
- `2` nodos de base de datos forman un clúster PostgreSQL + TimescaleDB primario/en espera.
- `1` nodo Witness participa en la supervisión de la base de datos, el cuórum y la conmutación por error.

La configuración simplificada reduce la complejidad del despliegue. A cambio, la capa de aplicación y EMQX son puntos únicos de fallo. Solo la capa de base de datos conserva la alta disponibilidad mediante `DB VIP + Witness`.

| Tipo | Nombre | IP planificada | Descripción |

## Topología general

<img width={650} src="https://enterpriseimage.oss-cn-hangzhou.aliyuncs.com/9.png" />

Rutas principales:

- Ruta de negocio: clientes / sistemas de la instalación → `ent-enterprise-01` → `DB VIP` → base de datos primaria actual.
- Tanto `tier0-enterprise` como `EMQX` se ejecutan en `ent-enterprise-01`.
- El acceso a la base de datos sigue pasando por `DB VIP`; se prohíbe el acceso directo de la aplicación a `ent-db-01/02`.
- `Witness` participa únicamente en el cuórum, la promoción y las comprobaciones de salud de la base de datos. No forma parte de la ruta de negocio.

## Supervisión de la base de datos y conmutación por error

| Fase | Ruta | Descripción |
| --- | --- | --- |
| Acceso normal | `ent-enterprise-01 -> DB VIP -> current primary` | La aplicación siempre se conecta a `10.60.20.10:5432` |
| Replicación normal | `current primary -> current standby` | Replicación en streaming de WAL de PostgreSQL |
| Supervisión normal | `DB-01/DB-02 -> Witness` | `repmgrd` informa del estado; Witness participa en el cuórum |
| Fallo del primario | `standby -> Witness` | El nodo en espera solicita confirmación del cuórum para evitar un escenario de cerebro dividido |
| Promoción del nodo en espera | `standby promote` | El nodo en espera se promueve tras la confirmación de Witness |
| Traslado de la VIP | `DB VIP -> new primary` | `10.60.20.10` se asigna al nuevo primario |
| Recuperación de la aplicación | `ent-enterprise-01 -> DB VIP -> new primary` | La aplicación se recupera cuando el pool de conexiones vuelve a conectarse |

## Recomendaciones de despliegue

### Nodo de aplicación enterprise

- No desplegar Docker Swarm.
- Desplegar `tier0-enterprise` y `EMQX` en el mismo nodo `ent-enterprise-01`.
- `ent-enterprise-01` es un punto único de fallo de la capa de aplicación. En caso de fallo, recuperar manualmente o reconstruir desde una copia de seguridad.
- El nodo solo tiene un disco de sistema de `100G` y no es adecuado para conservar datos de negocio a largo plazo.
- Los datos de negocio de `tier0-enterprise` deben guardarse en PostgreSQL/TimescaleDB.
- Los archivos de carga, importación/exportación e informes pueden guardarse localmente y respaldarse. Si más adelante se migra a la configuración estándar, trasladar estos archivos a NFS/NAS o almacenamiento de objetos.

### EMQX de un solo nodo

- En la configuración simplificada, EMQX es un servicio con estado de un solo nodo.
- Fijar su directorio de datos en `ent-enterprise-01`, por ejemplo `/data/emqx`.
- Realizar copias de seguridad de la configuración, los certificados, los plugins y la configuración del motor de reglas.
- No se proporciona alta disponibilidad de la capa de mensajería. Si esto no cumple los requisitos, utilizar la configuración estándar con un clúster EMQX de tres nodos.

### PostgreSQL + TimescaleDB

- PostgreSQL: `16` o la versión certificada para la instalación.
- TimescaleDB: versión estable compatible con la versión principal de PostgreSQL seleccionada.
- Replicación: replicación física en streaming.
- Conmutación por error: `repmgrd + witness`.
- Punto de entrada de la base de datos: `DB VIP`.
- Pool de conexiones: PgBouncer puede ejecutarse en `ent-enterprise-01` para reducir la carga de conexiones de la base de datos.

### Witness

- Witness solo almacena los metadatos de `repmgr witness` y la lógica de supervisión.
- Witness no ejecuta SQL de negocio.
- Un fallo de Witness no detiene el primario actual, pero reduce la fiabilidad de la conmutación automática por error.

## Capacidades de alta disponibilidad y límites ante fallos

| Escenario de fallo | Comportamiento esperado | Impacto en el negocio |
| --- | --- | --- |
| Fallo de `ent-enterprise-01` | Se detienen la aplicación y EMQX; se requiere recuperación manual o reconstrucción desde una copia de seguridad | Interrupción completa de la capa de aplicación |
| Fallo del primario actual de la base de datos | El nodo en espera se promueve tras el cuórum de Witness y DB VIP se traslada | Interrupción de escritura de segundos a minutos; la aplicación debe reconectarse |
| Fallo del nodo de base de datos en espera | El primario sigue prestando servicio y se genera una alerta de replicación | Sin interrupción directa del negocio, pero se pierde el nodo de reserva en caliente |
| Fallo de Witness | El primario actual sigue prestando servicio, pero disminuye la fiabilidad de la conmutación automática por error | Sin interrupción directa del negocio; recuperar Witness primero |
| Fallo en el traslado de DB VIP | Puede existir un nuevo primario, pero el punto de entrada unificado no es accesible | Interrupción del negocio; se requiere asignar la VIP manualmente |

## Orden de implementación

1. Crear 4 máquinas virtuales y fijar nombres de host, IP, sincronización horaria y SSH.
2. Inicializar la configuración base del sistema operativo, el cortafuegos, los puntos de montaje y los parámetros del kernel.
3. Desplegar `tier0-enterprise` en `ent-enterprise-01`.
4. Desplegar EMQX de un solo nodo en `ent-enterprise-01`.
5. Desplegar PostgreSQL + TimescaleDB con nodos primario y en espera.
6. Desplegar repmgr witness, repmgrd y los scripts de traslado de DB VIP.
7. Verificar conectividad, recuperación de EMQX, conmutación por error de base de datos, restauración de copias y comprobaciones rutinarias.
8. Completar los Runbooks de operaciones, el archivo de credenciales y las tareas de revisión rutinaria.

## Riesgos y cuestiones pendientes

- La configuración simplificada tiene un punto único de fallo en la capa de aplicación. Si falla `ent-enterprise-01`, todo el servicio de negocio queda inaccesible.
- EMQX tiene un solo nodo y no proporciona alta disponibilidad de la capa de mensajería.
- `ent-enterprise-01` solo tiene un disco de sistema de `100G`. Es necesario controlar registros, caché, adjuntos y archivos temporales.
- Si más adelante se necesita alta disponibilidad de la capa de aplicación o de EMQX, migrar a la configuración estándar.
- El RPO/RTO de la base de datos no está confirmado. Este diseño primario/en espera no garantiza la ausencia de pérdida de datos.
- Los scripts de traslado de DB VIP deben verificarse en la instalación, especialmente si la plataforma de virtualización/red permite VRRP.
