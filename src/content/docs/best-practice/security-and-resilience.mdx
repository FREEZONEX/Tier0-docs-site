Tier0 ensures data security through the following aspects:

- **Security**: Controls who can access the platform, applications, and data.
- **Resilience**: Covers service continuity and data recovery after failures.

## Security Scope by Edition

| Edition | Security Coverage |
| --- | --- |
| **Cloud** | Platform access control and authenticated access to MQTT and APIs. |
| **Enterprise** | Platform and data access control, plus deployment availability, backup, and recovery for private deployments. |
| **Edge (open source)** | Local data connection and modeling. Its built-in MQTT broker allows unauthenticated subscriptions. |

See [Choosing the Best Product](https://tier0.app/pricing) for edition positioning.

## Security

### Identity and Access Control

| Area | Tier0 Mechanism | Details |
| --- | --- | --- |
| Platform access | <ul><li>Cloud controls access through workspace membership.</li><li>Enterprise controls access through user accounts.</li></ul> | [User Management](../../reference/user-management/) |
| Agent access | Agents authenticate with an API key and use the Tier0 CLI to access and operate the platform. | [CLI authentication](/using-tier0/operating-on-tier0-with-agents/#authentication) |
| Project and application access | Tier0 uses RBAC to control access to applications. | [Access control](/using-tier0/building-apps/#access-control) |

:::note
Workspace membership does not automatically create an account. You still need to register and sign in to your own accounts. Account registration requires two-factor verification.
:::

### Data Access Control

| Access | Tier0 Mechanism | Details |
| --- | --- | --- |
| MQTT | <ul><li>Clients authenticate with credentials generated by Tier0.</li><li>TLS and secure WebSocket encrypt data in transit.</li></ul> | [MQTT credentials and connections](/using-tier0/working-with-factory-data/#generating-mqtt-credentials) |
| REST API | Accessing data requires a key generated by Tier0. | [API Reference](../../reference/api-reference/) |

## Resilience

### Deployment Availability

Enterprise currently provides two deployment plans for center nodes:

| Plan | Availability Boundary | Details |
| --- | --- | --- |
| **Standard deployment** | <ul><li>Provides database primary/standby failover.</li><li>The Enterprise application and EMQX remain single points of failure.</li></ul> | [Standard Deployment Plan](../../reference/standard-deployment-plan/) |
| **High availability deployment** | <ul><li>Adds active/standby Enterprise nodes and defined failover behavior for the database, cache, object storage, and managed runtime files.</li><li>Does not promise zero interruption or zero data loss.</li></ul> | [High Availability Deployment Plan](../../reference/high-availability-deployment-plan/) |

:::note
Detailed availability limitations are documented in [SLA and High Availability Boundaries](../../reference/sla-and-ha-boundaries/).
:::

### Backup and Recovery

Enterprise provides database backup and recovery. After recovery, check deployment status, run basic functionality checks, and confirm that users can sign in to the platform.

- For backups, see [Backup and Restore](/reference/operations-runbook/#backup-and-restore).
- For recovery verification requirements, see [Drill Requirements](/reference/sla-and-ha-boundaries/#drill-requirements).

:::note[Response time]
The typical response time is 3 business days.
:::
